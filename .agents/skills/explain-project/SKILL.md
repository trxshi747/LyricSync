# Explain Project Skill

You are helping a non-technical or semi-technical vibe coder understand the current project after Claude has been coding.

Your job is to inspect the repository and create a clear Markdown file explaining what is going on.

Default output file:

`PROJECT_EXPLAINED.md`

If the user passes a Markdown filename in `$ARGUMENTS`, use that as the output file instead. Otherwise use the default.

If the user passes a focus area in `$ARGUMENTS`, such as `auth`, `frontend`, `database`, `payments`, or `recent changes`, emphasize that area while still producing the full explanation.

## Hard rules

- Do not modify application code.
- Do not modify configuration files.
- Do not install dependencies.
- Do not run migrations.
- Do not create commits.
- Do not delete files.
- Do not expose secret values.
- Only create or update the explanation Markdown file.
- If a `.env` file exists, never copy its values. Mention only variable names and whether they appear required.
- Prefer static inspection over running the app.
- If something is uncertain, say `Unknown` and explain what would need to be checked.
- Use plain English first, then technical detail.
- Explain jargon the first time it appears.
- Every important claim should reference real files or folders using relative paths in backticks.

## What to inspect

Inspect the project in this order:

1. Repository basics:
   - current directory
   - whether this is a git repository
   - top-level files and folders
   - README files
   - documentation files

2. Project type:
   - language or languages
   - framework
   - package manager
   - build tool
   - runtime
   - deployment hints

3. Important files:
   - `package.json`
   - `pnpm-lock.yaml`
   - `yarn.lock`
   - `package-lock.json`
   - `pyproject.toml`
   - `requirements.txt`
   - `Cargo.toml`
   - `go.mod`
   - `composer.json`
   - `Gemfile`
   - `Dockerfile`
   - `docker-compose.yml`
   - `.github/workflows/*`
   - framework config files
   - routing files
   - database/schema files
   - environment examples such as `.env.example`

4. Source structure:
   - main app entry point
   - routes/pages/controllers
   - components
   - services
   - database layer
   - API clients
   - auth logic
   - tests
   - styling
   - public/static assets

5. Recent Claude work:
   - inspect `git status --short`
   - inspect `git diff --stat`
   - inspect relevant uncommitted diffs
   - inspect recent commits if available
   - explain what appears to have changed in plain English

6. How to run the project:
   - infer commands only from real files like `package.json`, README, Makefile, Docker files, or project config
   - do not invent commands
   - separate install, dev, build, test, lint, and deploy commands where possible

7. Risks and unknowns:
   - missing README
   - missing tests
   - unclear environment variables
   - uncommitted changes
   - hardcoded values
   - broken or incomplete flows
   - files that look generated
   - fragile areas a beginner should avoid touching

## Output format

Create or update the output file using this exact structure:

```markdown
# Project Explained

Generated by Claude Code using `/explain-project`.

## 1. Plain-English Summary

Explain what this project appears to be in 3-7 sentences.

Avoid jargon. If jargon is necessary, explain it.

## 2. What This Project Is Made Of

| Area | Files / Folders | What It Does | Why It Matters |
|---|---|---|---|
| Example | `src/` | Contains the main app code | This is where most changes happen |

Include only areas that actually exist.

## 3. Folder Map

Explain the most important folders.

Use this format:

- `folder/` — plain-English explanation.
- `folder/subfolder/` — plain-English explanation.

Ignore generated or dependency folders like `node_modules/`, `.next/`, `dist/`, `build/`, `coverage/`, `.git/`, and cache folders unless they are unusually important.

## 4. How The App Starts

Explain the likely entry point.

Include:
- the main command, if known
- the main file, if known
- what happens first when the app starts
- what files control routing or screens, if applicable

## 5. How The Main User Flow Works

Explain the most important user journey or system flow.

Use simple steps:

1. User does X.
2. The app sends/loads Y.
3. File `...` handles Z.
4. Data is saved/read from `...`.

If the flow is unclear, say so.

## 6. What Claude Recently Changed

Explain recent work based on git status, git diff, and recent commits.

Separate into:

### Changed files

| File | What Changed | Why It Probably Matters |
|---|---|---|

### Plain-English explanation

Summarize what Claude appears to have been doing.

If there are no uncommitted changes, say that.

## 7. Important Files To Know

| File | Why It Matters | Beginner Notes |
|---|---|---|

Include files someone should understand before asking Claude for more changes.

## 8. How To Run This Project

Only include commands that are supported by real project files.

Use this structure:

### Install

\`\`\`bash
command here
\`\`\`

### Run locally

\`\`\`bash
command here
\`\`\`

### Build

\`\`\`bash
command here
\`\`\`

### Test

\`\`\`bash
command here
\`\`\`

### Lint / format

\`\`\`bash
command here
\`\`\`

If a command is unknown, write:

`Unknown from the current files.`

## 9. Configuration And Environment Variables

List environment variable names only.

Never include secret values.

| Variable | Where It Appears | What It Probably Does | Required? |
|---|---|---|---|

## 10. Database / Storage

Explain whether the project appears to use a database, files, local storage, external APIs, or another storage method.

Mention relevant schema, migration, model, ORM, or API files.

## 11. External Services

List external services the project appears to use, such as:

- authentication providers
- payment providers
- email providers
- analytics
- databases
- AI APIs
- cloud storage
- deployment platforms

Only include services supported by actual files or dependencies.

## 12. Beginner Glossary

Explain important concepts in this project.

Example:

- **Component** — reusable piece of the user interface.
- **API route** — backend endpoint the frontend can call.
- **Environment variable** — configuration value kept outside the code, often secret.

Use terms that actually appear in this project.

## 13. Safe Things To Ask Claude Next

Give 5-10 useful prompts the user can ask next.

Examples:

- "Explain `src/app/page.tsx` line by line."
- "Show me where the login flow starts."
- "Add comments to the most confusing file without changing behavior."
- "Create a diagram of the data flow."
- "Before coding, make a plan for changing X."

Make these specific to the actual project.

## 14. Risk Map

| Risk | Where | Why It Matters | Safer Next Step |
|---|---|---|---|

Focus on things a vibe coder should be careful with.

## 15. Unknowns

List anything important that could not be determined from the current files.

For each unknown, explain how to find the answer.
```

## Writing style

Write for a smart beginner.

Use:
- short paragraphs
- concrete file references
- simple explanations
- no unexplained jargon
- tables where useful
- honest uncertainty

Do not write like an enterprise architecture document.

The goal is: after reading this file, the user should understand what Claude has been doing and what they can safely ask for next.

## Completion criteria

You are done when:

1. The explanation file exists.
2. It references actual project files.
3. It explains recent changes if git data is available.
4. It gives concrete run/test commands if discoverable.
5. It includes risks and unknowns.
6. It does not expose secrets.
7. It does not modify anything except the explanation file.
